A knowledge graph represents things as nodes and the relationships between them as labelled,
directed edges. A statement such as "Ada wrote Program" becomes a small graph: Ada and Program
are nodes, while *wrote* names the relationship. Many systems store statements like this as
subject, predicate, and object triples.

That simple shape matters because relationships remain available for questions. A reader can start
with one entity and follow paths to its suppliers, owners, locations, sources, or consequences. The
[Stanford CS520 introduction](https://web.stanford.edu/class/cs520/2020/notes/What_is_a_Knowledge_Graph.html)
uses this directed, labelled graph as its basic definition and shows how it supports information
integration and machine learning.

## Meaning is part of the graph

A collection of connected records is not automatically a useful knowledge graph. The identifiers
must refer to things consistently, and edge labels must have defined meanings. If two sources use
"Paris" for a person and a city, merging them by text alone creates false statements. If one source
uses *owner* for legal ownership and another uses it for operational responsibility, a shared label
hides a real distinction.

[Ontology engineering](/ideas/ontology-engineering) supplies classes, relationships, and
constraints when the graph needs them. The ontology does not have to be large or universal. A
small vocabulary that preserves the distinctions needed for a task is often better. Different
[bounded contexts](/ideas/bounded-context) may keep different models and publish explicit mappings
where they overlap.

Identity is a separate problem. Stable identifiers let several names refer to the same entity, but
entity resolution is an interpretation rather than a clerical step. A match should retain its
evidence and confidence. Extraction methods such as [named entity recognition](/ideas/ner) can
propose nodes and relationships, while review or later evidence can correct them.

## A graph model is not a graph database

A graph database is storage and query technology. A knowledge graph is a representation whose
nodes and relationships carry defined meaning. It can live in a graph database, relational tables,
documents, or files. Conversely, a graph database used for routing or dependency calculation does
not become a knowledge graph merely because it contains nodes and edges.

A taxonomy is narrower too. It arranges concepts into broader and narrower categories. A knowledge
graph can include those categories alongside many other relationships between classes, individual
entities, events, and sources.

## Claims need context

Real graphs combine statements that came from different places and may disagree. Treating every
edge as timeless fact makes the graph easy to query and hard to trust. Useful records often include
who or what asserted a statement, when it applied, when it was recorded, and which evidence
supports it. [Data provenance](/ideas/data-provenance) makes those origins and transformations
queryable.

This turns the graph into a collection of claims rather than an oracle. Queries can then choose the
sources, dates, and confidence levels appropriate to the decision. The graph may still be wrong,
but it can explain why it currently says what it says.

## Questions it prompts

* Which entities need stable identities across sources?
* What does each relationship mean, and in which context does that meaning hold?
* Which claims conflict, and should the system reconcile or preserve the disagreement?
* Can a result point back to the statements and sources that support it?
* Would a simpler table or document model answer the required questions more clearly?

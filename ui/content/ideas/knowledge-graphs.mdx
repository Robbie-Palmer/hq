A knowledge graph describes knowledge as identifiable entities joined by named relationships. A
statement such as "Ada wrote Program" can be represented as a subject, predicate, and object:
*Ada*, *wrote*, *Program*. The predicate says what the link means. It is more than an anonymous
line between two records.

There is no single agreed definition of a knowledge graph. The
[Stanford CS520 introduction](https://web.stanford.edu/class/cs520/2020/notes/What_is_a_Knowledge_Graph.html)
starts with a directed, labelled graph whose labels have well-defined meanings. Other definitions
also require a schema, links across sources, or methods for deriving new statements. These
differences produce several kinds of knowledge graph, including RDF graphs and labelled property
graphs.

## Predicates carry meaning

In a knowledge graph, relationship names belong to the knowledge model. *Wrote*, *employed by*,
and *located in* describe different claims and support different questions. A query can match a
particular predicate or a path made from several predicates, such as a work, its author, and the
author's birthplace.

RDF uses global identifiers called IRIs for predicates, and permits subjects and non-literal
objects to use them too. Two publishers can therefore refer to the same predicate or entity
without sharing a database schema. Labelled property graphs usually use names that are local to
one graph, although applications can impose wider naming rules. In either case, merging graphs
safely depends on knowing whether two identifiers denote the same thing and whether two predicates
express the same relationship.

[Named entity recognition](/ideas/ner) can find candidate entities in text. Entity resolution then
decides whether two mentions refer to one entity. That decision is part of constructing the graph,
and mistaken matches create mistaken paths.

## Schemas can support inference

[Ontology engineering](/ideas/ontology-engineering) defines classes and predicates when a graph
needs shared semantics. In RDF Schema or OWL, those definitions can also entail statements that
were never stored directly. If every *archivist* is a *person*, and Jo is an archivist, a reasoner
can infer that Jo is a person. Rules can define inverse relationships, class hierarchies, and other
consequences.

Reasoning is optional. Many knowledge graphs use a lightweight vocabulary and answer only what
their recorded statements support. Others use formal ontologies and an entailment regime. Readers
need to know which behaviour a graph provides, because an inferred answer has a different basis
from an asserted one.

## The graph is the query model

Knowledge-graph query languages match graph-shaped patterns. SPARQL matches sets of RDF triples;
property-graph languages match nodes, edges, labels, and paths. This makes a chain of named
relationships a direct part of the query rather than an implementation detail hidden behind one
application endpoint.

Relational tables can represent the same facts, and SQL can follow relationships through joins or
recursive queries. The choice of a knowledge graph adds neither truth nor expressive power by
itself. It makes entities, predicates, and graph patterns the shared model presented to publishers
and consumers. A graph database is one possible storage engine for that model. It can also store a
network with no knowledge model at all.

## Statements can have their own context

Graphs assembled from several sources often contain competing or time-bound claims. RDF named
graphs, reification, and similar techniques let a system identify a statement or a set of
statements, then attach a source, time, or confidence to it. [Data provenance](/ideas/data-provenance)
explains the broader job of recording where data came from and how it changed.

This context matters when the graph answers through several links. A useful result should expose
which statements supported the path and whether any were inferred. Otherwise the graph can return
a connected answer without showing why anyone should accept it.

## Questions it prompts

* Do entities and predicates have identities that can be reused across sources?
* Which meanings come from an ontology, a local schema, or application convention?
* Does the graph return asserted statements, inferred statements, or both?
* Which path patterns need to be queried across independently published data?
* Would tables and ordinary joins give consumers a simpler model for the same facts?

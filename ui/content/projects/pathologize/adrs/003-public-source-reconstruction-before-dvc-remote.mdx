## Context

Pathologize must reproduce a pinned registry revision without treating public
availability as permission to republish whole-slide images. The initial
registry proves two different cases. It can download one 18.7 MB IDC series
from pinned public URLs and verify every file against a declared byte count and
SHA-256 digest. CAMELYON16 and PANDA remain manifest-only because collection
size, historical rules, authentication, or access terms require operator
review.

[ADR 000](/projects/pathologize/adrs/000-standards-based-pathology-data-boundary)
keeps registry references separate from image bytes, and
[ADR 001](/projects/pathologize/adrs/001-resource-and-cost-contract-boundary)
keeps provider funding outside benchmark manifests. The platform selects DVC
for artifact versioning, but its
[DVC decision](/projects/personal-engineering-platform/adrs/024-dvc-artifact-versioning)
leaves the provider, access boundary, retention, and backup policy to each
adopter.

The repository has three realistic storage patterns. Established ML pipelines
use private prefixes in the shared Cloudflare R2 DVC bucket. Home Lab has used
a machine-owned DVC cache. The Pathologize registry reconstructs a bounded
fixture from its public publisher. Backblaze B2 also backs the independent
personal archive, but that archive needs provider separation and Object Lock.
Pathologize has neither requirement today.

## Decision

Do not configure a shared DVC blob remote for the Pathologize registry or its
initial benchmark projects yet. Use an ignored machine-owned filesystem remote
when a working copy needs DVC artifact persistence. Preserve public registry
metadata, licence and access records, source URLs, byte counts, SHA-256
digests, DVC definitions, and lock data in Git. The named publisher remains
the byte distribution authority. A materialized source file, machine-owned
remote, and DVC cache are verified, disposable copies. They do not publish a
new source. This satisfies the platform DVC policy without creating a hosted
data collection.

Use the asset-manifest SHA-256 digest as the source-integrity check. DVC's
content hash binds the materialized output to a pipeline revision, but it does
not replace the source digest, licence record, or retrieval evidence. If the
publisher removes or changes a pinned object, mark that registry revision
unavailable until a permitted source with the same SHA-256 is documented. Do
not silently bless different bytes or upload a surviving local copy.

Keep public metadata and source bytes on opposite sides of the access
boundary:

* Git may contain manifests, citations, access terms, public source identities,
  checksums, and synthetic fixtures. It must not contain clinical slide bytes.
* Automated acquisition is limited to allowlisted public HTTPS objects whose
  manifests permit it. This path uses no paid model or API.
* Gated, authenticated, restricted, or legally unclear collections remain
  manifest-only in the public registry. An operator may materialize them
  locally after accepting the source terms, but must not put them in the shared
  DVC bucket.
* Derived tiles, masks, embeddings, and model outputs inherit the source
  licence and access restrictions until a documented review permits a wider
  distribution. Public viewer assets need that review even when the source was
  free to download.

For local and offline work, configure the filesystem remote in
`.dvc/config.local`, then acquire and verify permitted source bytes while the
publisher is reachable. Add the verified, DVC-tracked stage outputs to the DVC
cache before pushing them to that remote. Move the remote or cache only through
a route allowed by the collection terms. A clean machine with neither the
publisher nor an approved local remote cannot reproduce the bytes, and the
project must report that limit instead of fetching from an unrecorded mirror.

Delete reconstructable public bytes when no pinned local experiment needs
them. Restricted bytes stay only for the approved study or the shorter period
set by their source terms. An access withdrawal or deletion obligation
requires removing the working copy, DVC cache, and any local filesystem
remote. Keep a public tombstone with the source identity, digest, and reason
only when the terms permit that metadata. Recovery tries the pinned publisher
first, then an approved offline cache with the same SHA-256.

This decision adds no recurring provider charge. Contributors still supply
their own disk, download bandwidth, and compute. A hosted remote would create a
new storage and operations commitment, so it needs separate owner approval.

## Migration gate

Cloudflare R2 is the preferred hosted remote if public-source reconstruction
stops meeting a concrete durability need. Use a private Pathologize bucket or
prefix, separate from public viewer assets and from collections with different
rights. Reusing the repository's R2 integration is less operational work than
adding Amazon S3 or Backblaze B2, and it follows the platform's
[object-storage decision](/projects/personal-engineering-platform/adrs/016-cloudflare-r2-object-storage).

Do not change registry commands or CI to pull or push that remote until a
follow-up change provides all of this evidence:

1. A named collection or derived artifact needs durability that its publisher
   and approved offline copies cannot provide.
2. A collection-by-collection review records whether shared storage and any
   later redistribution are permitted. Restricted and redistributable bytes
   have separate access and lifecycle boundaries.
3. The owner approves the expected storage, request, and transfer cost. The
   proposal does not depend on a paid model or inference API.
4. Reviewed infrastructure provisions the storage, and Doppler supplies
   bucket-scoped read and write credentials. Delete or lifecycle authority uses
   a separate identity where the provider supports that split.
5. A restore drill reproduces a pinned registry revision in a clean checkout,
   verifies the asset SHA-256 values, and proves the local or offline path
   without exposing credentials or restricted bytes.
6. A deletion drill removes an expired object and its recoverable copies
   without touching another project or rights class. Retention, backup,
   incident recovery, and upstream-loss procedures are written before CI gains
   remote access.

Until that gate passes, CI validates public metadata and synthetic fixtures.
On a clean runner, the registry check also acquires the public six-file
CPTAC-COAD DICOM series when it is absent. CI does not require DVC remote
credentials.

## Consequences

The current registry remains reproducible without creating a quiet second
publication of pathology data. Public Git history preserves the identities and
digests needed to detect source drift, while operators retain an explicit
offline option for permitted bytes.

An upstream deletion can make an old revision impossible to reproduce from a
fresh checkout. Local caches reduce that risk but do not count as durable
shared storage. The project accepts that limitation for the bounded starter
corpus instead of paying for storage or crossing a licence boundary before a
real durability need exists.

Adding R2 later will require policy and operational work before the first
upload. That cost is deliberate. The remote cannot become the default merely
because another repository pipeline already has credentials.

## Alternatives considered

### Use the shared private R2 DVC bucket now

This matches the established WSI and evaluation pipelines and would protect
against upstream loss. It would also copy clinical source bytes before the
project has a durability requirement, collection-specific upload review,
retention rule, deletion drill, or approved cost. R2 is reserved for migration
after the gate passes. The publisher remains the current source of bytes.

### Keep only a machine-owned DVC remote

An ignored filesystem remote is useful for offline runs and restricted data.
It cannot prove that another contributor can recover an old revision, and one
disk failure can remove it. The project treats it solely as a permitted local
copy. It provides no shared durability.

### Add Backblaze B2 or Amazon S3

B2 fits the repository's independent archive because that system needs a
second provider and retention controls. Amazon S3 offers the native source
interface for some public datasets. Neither gives Pathologize a current
requirement that outweighs another account, credential boundary, and operating
path. If R2 later fails a measured need, a new ADR can compare providers using
that evidence.

title: "ADR 001: Resource and cost contract boundary"
date: "2026-11-06"
status: "Accepted"
---

## Context

The first benchmark manifests used `paid_api_calls_allowed` and
`max_paid_api_calls`. Scorecards then recorded a zero call count. A call count
does not express price, currency, prepaid access, metered usage, or who may
authorize spending. It also puts orchestration policy inside an adapter
description.

The Agent Coordinator already models money as a non-negative amount with an
ISO-style three-letter currency code. It distinguishes prepaid and metered
provider use, records measured provider-request cost, and tracks resource
quantities independently. Rewriting a smaller Python version in Pathologize
would create two contracts with the same names and different release cycles.

[ADR 000](/projects/pathologize-benchmarks/adrs/000-standards-based-pathology-data-boundary)
keeps registry ownership outside the benchmark package. Cost needs the same
kind of ownership boundary.

## Decision

Remove paid-inference permission and call-count fields from Pathologize adapter
specifications, resource budgets, resource usage, and scorecards.

Pathologize continues to own benchmark-specific resource limits and
measurements: input bytes, prediction bytes, pixels read, accelerator seconds,
wall time, CPU time, and peak resident memory. These quantities affect whether
a candidate is practical on the benchmark workload.

Provider funding, account policy, and spending authorization remain in the
orchestrator. If a future benchmark adapter uses metered inference, extract the
existing `Money` and `ResourceQuantity` semantics into a versioned JSON Schema
2020-12 contract owned by the platform. TypeScript and Python bindings must
validate the same examples and generated schema. The benchmark scorecard will
record observed monetary cost by currency. The orchestrator will continue to
decide whether payment is allowed.

Do not publish a Pathologize money field before a real adapter needs it. The
current deterministic baselines make no provider calls.

## Consequences

Benchmark manifests describe experiments instead of account policy. A free,
prepaid, or metered route can run the same adapter without changing its model
identity.

The current scorecard cannot compare monetary cost. That is deliberate. Bytes,
pixels, time, and memory remain available now, while provider pricing waits for
a shared cross-language contract and a measured use case.

Adding cost later will require a scorecard schema revision and cross-language
contract tests. It will also need a clear rule for estimates, final charges,
currency conversion, and missing provider cost data.

## Alternatives considered

### Keep a boolean permission field

A boolean is easy to validate, but authorization depends on the owner, account,
budget, and route. The adapter cannot answer that question.

### Keep a maximum provider-call count

Calls can have different token, image, model, and provider prices. A count is
neither a cost budget nor a stable resource comparison.

### Copy the coordinator's money shape into Python

This would produce a field immediately. It would not produce a shared contract.
The first later change could leave Zod and Pydantic accepting different data.
The project waits for one language-neutral schema instead.

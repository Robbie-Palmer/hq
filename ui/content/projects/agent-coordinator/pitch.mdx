# Keep valuable agent work moving

Agent Coordinator puts available reasoning capacity onto the most valuable
automatable software-development work and carries it through a verified
outcome.

<PitchNotes>
  Paid plans provide a changing pool of reasoning capacity. Tasks become ready, limits reset, and agents finish work
  at different times. The coordinator decides what can use that capacity now and remains responsible for the result.

  \[Sources]

  * [Agent Coordinator vision](/projects/agent-coordinator?tab=overview#vision)
    \[/Sources]
</PitchNotes>

***

## The scarce resource is human judgment

The first pilot launched general Work Graph tickets. It found plenty of work,
but much of it involved exploratory architecture, UX, or prose that still
needed a person to judge the result.

<p className="pitch-slide__statement">Cheap agent output becomes expensive when it only fills a human review queue.</p>

<PitchNotes>
  The project should prefer work that agents can finish and evaluate. It should route genuine product, design,
  architecture and editorial decisions to people instead of manufacturing drafts because capacity is idle.

## Keep planning, coordination, and execution separate

<PitchColumns>
  <PitchColumn>
    ### Work Graph

    Desired outcomes, priority, dependencies, leases, and durable evidence.
  </PitchColumn>

  <PitchColumn>
    ### Agent Coordinator

    Admission policy, capacity allocation, continuity, authority, and outcome evaluation.
  </PitchColumn>

  <PitchColumn>
    ### Agent runtime

    Providers, sessions, threads, worktrees, limits, and interruption recovery.
  </PitchColumn>
</PitchColumns>

<p className="pitch-slide__statement">The plan stays durable while execution machinery and model capacity change.</p>

<PitchNotes>
  Provider names and subscription limits should not leak into the durable work model. The coordinator interprets the
  plan and current capacity, while the runtime handles agent execution.

## Use the capacity already available

* Match task requirements to capable agents and models
* Notice newly available work and safe parallelism
* Track subscription limits and reset times
* Resume useful work after limits, restarts, and interruptions
* Avoid launching work whose result still needs open-ended human review

<p className="pitch-slide__statement">Measure completed outcomes, not active threads or consumed tokens.</p>

<PitchNotes>
  The long-term goal is continuous allocation across automatable SDLC work. Capacity is useful only when it shortens
  the route to a result the system can verify.

## T3 Code replaces custom execution machinery

T3 Code already supplies signed webhook automations, controller and worker
threads, managed worktrees, provider sessions, pull-request watches, usage-limit
recovery, and continuation after restarts.

<p className="pitch-slide__statement">Build coordination policy and outcome loops instead of maintaining a second agent runtime.</p>

<PitchNotes>
  The current Work Graph poller, launcher and provider-session package remain useful during migration. Limit changes
  to maintenance for existing users. Remove them after the T3 path replaces their live uses, then rely on Git history
  instead of maintaining two permanent fallbacks.

## Start with severe vulnerability remediation

GitHub provides the security signal. Renovate provides deterministic update
proposals. Agent Coordinator owns the judgment and delivery work that remains.

<Mermaid
  chart={`flowchart LR

Inspect --> Fix[Repair or create the fix]
Fix --> Merge[Pass checks and merge]
Merge --> Deploy[Deploy]
Deploy --> Validate[Validate production]
Validate -->|failure| Fix
`}
/>

<p className="pitch-slide__statement">Security remediation is the first product vertical. The project covers the wider automatable SDLC.</p>

<PitchNotes>
  Vulnerability remediation has a clear trigger and an observable production result. It exercises the complete
  coordination loop without depending on a person to assess every intermediate artifact.

## Give the agent enough authority to finish

The worker may repair or replace a Renovate pull request, merge after required
checks, follow the established deployment path, validate production, and repair
or revert a failed rollout.

It asks for help when authority is missing or the safe result remains ambiguous.

<p className="pitch-slide__statement">A pull request is intermediate. The product is a verified outcome.</p>

<PitchNotes>
  Branch protection and deterministic checks remain in force. The agent cannot dismiss the alert, weaken those
  controls, or claim success because a change merged without proving what reached production.

  \[Sources]

  * [Authority model](/projects/agent-coordinator?tab=overview#authority-model)

## Prove one vertical, then expand across the SDLC

After vulnerability remediation, apply the same coordination to failing
delivery workflows, production regressions, dependency migrations, stale
high-value pull requests, and codebase analysis followed by bounded refactoring.

<p className="pitch-slide__statement">Expand when the next task class has an objective completion test.</p>

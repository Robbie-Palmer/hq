## Context

[ADR 013](/projects/personal-engineering-platform/adrs/013-build-runtime-standards)
separates workload packaging from orchestration and deployment targets.
[ADR 040](/projects/personal-engineering-platform/adrs/040-executable-project-profile)
reserves workload capabilities for a later profile version. The missing
contract must cover Cloudflare serverless workloads, NixOS services, local
containers, K3s, and Kubernetes without making Kubernetes a prerequisite for
every project.

The spike used one container service with an image, HTTP port, liveness and
readiness checks, CPU and memory bounds, literal configuration, a secret-bearing
PostgreSQL dependency, ingress, OTLP settings, and an ordered migration. The
package-owned `portable-workload-v0.yaml` fixture was projected to
`score-v1b1.yaml`, then rendered with `score-compose` 0.49.0 and `score-k8s`
0.22.0. A platform-contract test keeps the two fixtures aligned. The generated
manifests, implementation state, and credentials are not repository inputs.

## Decision

Use a small, versioned, repository-owned workload contract as the source for a
future project-profile capability. Keep it inside `packages/platform-contracts`
and parse it with the existing Zod boundary when that standard is implemented.
The fixture under `packages/platform-contracts/tests/fixtures/workload` records
version 0 evidence and does not define the accepted schema.

The contract owns portable intent: runtime family, artifact identity, process,
ports, health checks, resource bounds, configuration and secret references,
dependencies, ingress intent, telemetry contract, ordered migrations, and the
requested deployment targets. It never owns secret values, generated resource
names, provider identifiers, namespaces, Kubernetes object shapes, or release
state.

For a container workload, allow the compiler to emit Score `v1b1` as an
intermediate format. Score has a focused
[workload schema](https://docs.score.dev/docs/score-specification/score-spec-reference/)
and reference implementations for
[Compose and Kubernetes](https://docs.score.dev/docs/score-implementation/).
Do not make a handwritten Score file the project source. Resource types are
implementation-defined, the two implementations support different semantics,
and their local state carries generated identity and credentials.

Keep Kubernetes in an optional deployment-target layer. After a Kubernetes
renderer produces ordinary resources, use Kustomize overlays for
environment-specific changes. A project may package a Helm application chart
when it needs a distributable Kubernetes application or Helm's release,
upgrade, rollback, and hook behavior. The platform will not require a shared
Helm library chart or starter.

Do not select Open Application Model, KubeVela, or Devfile. Do not add CUE to
the source-contract toolchain. Revisit CUE only if the target generators need
cross-field unification that becomes awkward in TypeScript and Zod.

## Prototype findings

Both Score implementations accepted the same workload. Kubernetes retained all
resource bounds and probes, converted the migration to an init container,
stored the database password in a Secret, and produced an HTTPRoute. Compose
retained the migration completion dependency and built a local PostgreSQL
service and route, but it ignored CPU and memory bounds and HTTP probes with
warnings. It also placed the generated database password in local Compose
state and environment values.

This is useful divergence. Score preserves enough shared intent to justify an
adapter, while proving that target capability checks cannot stop at schema
validation. A project asking for a required probe or resource limit must fail
resolution for a target that ignores it. Silent degradation is not an
acceptable production render.

Score's provisioner state made repeated renders byte-identical. A fresh state
directory generated different database names, credentials, and route names.
The platform must therefore separate deterministic compilation from stateful
resource provisioning. Provisioners may resolve reviewed references during
deployment, but generated credentials and identity never enter the blueprint
or repository.

## Consequences

The workload-definition standard can start with the version 0 field set and
turn it into a strict version 1 schema. It must define required-versus-preferred
target semantics, reject unsupported required capabilities, and test each
adapter against the same conformance fixtures.

Projects can use Compose for local container development, K3s or Kubernetes for
cluster deployment, NixOS for host services, and Cloudflare for serverless work
without pretending those targets have identical controls. Kubernetes projects
may add Kustomize overlays or a Helm application chart after rendering without
leaking those formats into the portable profile.

The platform now owns a modest adapter layer. That cost is deliberate. It is
smaller than operating KubeVela for every workload and safer than making
implementation-defined Score resources or Helm values the permanent project
contract.

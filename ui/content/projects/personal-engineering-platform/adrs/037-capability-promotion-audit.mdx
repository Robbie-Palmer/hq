## Context

The platform needs a closed inventory of recurring application capabilities
before a project profile can drive Copier. The earlier decisions established the
individual boundaries:

* [ADR 034](/projects/personal-engineering-platform/adrs/034-identity-and-access-capability-contracts)
  separates authentication, session transport, authorization, preview access,
  service authentication, and delegated agent access;
* [ADR 035](/projects/personal-engineering-platform/adrs/035-web-api-data-capability-contracts)
  separates browser state, HTTP implementation, API contracts, governance,
  relational access, migrations, and connection pooling; and
* [ADR 036](/projects/personal-engineering-platform/adrs/036-operated-capability-contracts)
  records state ownership and operational proof for storage, recovery, previews,
  telemetry, and alerts.

The manifest contains the dated policies and selections, while project
frontmatter contains adoption. The remaining gap is a common interpretation of
those records. A generator must distinguish a required technology from an
optional capability, a technology from a policy value, and a product-local
candidate from a platform default. It must do that without treating every
package used by one product as shared policy.

## Decision

Classify a selection at an explicit instant from its status, kind, and effective
slot policy:

* an accepted technology in a required slot is a **required default**;
* an accepted technology in a preferred slot is a **preferred capability**;
* an accepted non-technology selection is a **policy value**; and
* a proposed, rejected, or deprecated selection is a **project-local choice**
  until a later accepted decision promotes it.

The domain query implements this rule so profile resolution and tests use the
same classification. The manifest remains authoritative for the slot, effective
date, deciding platform ADR, source ADR evidence, origins, and prerequisites.
Adopters remain derived from dated project records. The audit does not copy an
adopter list into the manifest.

Telemetry remains four separate concerns: transport, storage, evaluation, and
delivery. Product analytics does not activate operational logging, and a stored
log does not claim that the alerting path evaluated or delivered an alert.

### Choices not promoted

GitHub OAuth and delegated Agent Auth stay project-local because each has one
origin and neither has enough independent evidence for a default. They remain
proposed manifest records so a later decision can promote them without losing
provenance.

Query keys, routes, request schemas, database tables, migration contents,
preview fixtures, retention periods, recovery objectives, alert thresholds,
responders, and notification channels also stay local. They encode product
semantics or operating policy rather than a recurring implementation job. The
platform records the need for those values, not a shared value that would
silently fit one product to another.

### Adoption and override boundary

A project adopts a preferred capability by naming one slot in its layer record.
A local ADR may override that slot for a dated period while every other slot in
the layer continues to resolve normally. Required slots still apply unless the
project records a valid override. Closing the override returns the project to the
current platform selection. Existing resolver tests cover technology and policy
overrides, single- and multi-valued slots, prerequisite withholding, overlapping
period rejection, and return to the default.

## Alternatives

Classifying every accepted technology as a default would make optional jobs look
mandatory. A static site would inherit server state, a public API would inherit a
compatibility promise, and a stateless preview would inherit a database.

Using adoption count alone would promote incidental product choices and reject
required controls that apply to a narrow layer. The promotion test instead uses
an architectural job, a stable slot, credible alternatives, evidence, and a
decision to recommend the result.

Keeping the classification only in this ADR would force the project-profile
resolver to recreate the rules. The domain query makes the interpretation
deterministic while this record preserves why the rule exists and what the audit
included.

## Consequences

This decision closes the capability-gap audit without merging authentication,
authorization, API, data, or telemetry jobs. The future project profile can
consume one classification rule and carry each selection's dated policy,
evidence, prerequisites, and adopters.

The audit takes a conservative line. A project-local choice needs another
accepted platform decision before generation can offer it as a default. New
candidate families require another audit or a focused capability decision rather
than an unreviewed manifest entry.

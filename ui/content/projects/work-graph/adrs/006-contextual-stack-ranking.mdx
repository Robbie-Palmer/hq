## Context

[PDR 002](/projects/work-graph/pdrs/002-rank-work-in-context) defines the
product behaviour: local relative moves, one queue that can interleave scopes,
and explicit reason-bearing expedites. The service needs a deterministic data
model and projection that implements that behaviour without exposing internal
scores as the authoring interface.

Priority must flow through planning scopes, decomposition, and dependencies.
The projection also needs stable tie-breaking and enough provenance for a
client to explain why an item moved.

## Decision

Maintain separate ordinal stacks for initiatives, projects, and tickets.
Initiatives rank against initiatives, projects rank against projects, and a
ticket ranks only against tickets in the same scheduling project. New entries
start at the median. Relative move commands update one stack, and the service
may renormalise its stored rank numbers.

Each priority-owning ticket stores one scheduling project and, when needed, one
scheduling initiative. Infer the initiative when its project has exactly one
initiative parent. Require it explicitly when the project has several.
Decomposed work inherits its owning ticket's scheduling position, so graph
depth does not create another rank.

Fuse the three ordinal positions with reciprocal-rank fusion. Give initiative,
project, and ticket rank equal influence and use an offset of 10:

```text
score = 1 / (10 + initiative rank)
      + 1 / (10 + project rank)
      + 1 / (10 + ticket rank)
```

Sort higher scores first. Missing dimensions use the median position in that
stack. Structural child rank and stable work-item ID break ties. Fixture-driven
tests define the expected ordering, including a leading ticket in a
lower-ranked initiative outranking later tickets from a higher-ranked one.

Store expedite state and its required reason separately from ordinal rank.
Expedited tickets sort ahead of the fused queue. Project their effective
urgency onto unresolved blockers, with the source ticket recorded as
provenance. Removing the source expedite removes the donated urgency without
changing blocker ranks.

## Consequences

The public API accepts relative moves but does not expose the fusion score as a
stable contract. Read models include the three source positions and
expedite-donation provenance so clients can explain the projected order.

The queue can move when any surrounding stack changes. Representative fixtures
must protect the policy from accidental changes to the offset, missing-rank
handling, or tie-break order.

Moves across ticket projects or across unlike scope types are invalid because
they have no shared ordinal stack. Structural graph edits and scope assignment
must preserve the stored scheduling owner used by the projection.

## Alternatives considered

### Strict lexicographic ordering

Ordering initiative, then project, then ticket is deterministic but groups
whole subtrees and cannot provide the interleaving required by PDR 002.

### Weighted numeric priority

A weighted sum can produce the same broad ordering. It makes scale and
normalisation part of the stored interface and is more sensitive to rank gaps.
Reciprocal-rank fusion uses positions and tolerates rank renormalisation.

### Permanent pairwise constraints

Storing every above and below statement preserves commands as data but creates
a second graph that can become cyclic or dense. Relative moves update one
maintained ordinal stack instead.

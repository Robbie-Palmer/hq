# Context

[PDR 004](/projects/personal-knowledge-graph/pdrs/004-product-led-growth-learning-loop)
requires a product-led growth learning loop across the public graph and its
incubated products. Cloudflare Web Analytics supplies page counts and top paths,
but it does not provide custom events, funnels, experiments, or feature flags.

The first implementation needs:

* browser event capture for static pages;
* funnels and dashboards over custom events;
* an experiment and feature-flag path without another client SDK;
* EU data residency;
* a free tier that fits the current traffic; and
* a way to keep the analytics endpoint on the site's domain.

The platform choice does not authorise every capability it offers. Session
replay, surveys, identification, and new data categories still need their own
product and privacy review.

# Decision

Use **PostHog** as the analytics and product-telemetry platform.

Integrate the browser through `posthog-js`. Send its traffic through the site's
`/ingest/*` route to PostHog's EU endpoint. The first-party route keeps one
application endpoint and avoids coupling components to the vendor hostname. It
does not bypass a visitor's consent or privacy choice.

Use custom events, funnels, dashboards, experiments, and feature flags only as
required by an accepted product question. Keep event names and properties in
reviewed application code. Cloudflare's aggregate analytics remains a useful
secondary count because no browser SDK observes every request.

# Alternatives considered

## Cloudflare Web Analytics

It is already available, free, and does not require the application SDK. It
lacks the custom events, funnels, experiments, and feature flags required by
the decision.

## Google Analytics 4

GA4 has a large ecosystem and capable traffic reporting. Its advertising
business, consent burden, and separate experimentation path make it a poor fit
for this site's privacy boundary and small operating model.

## Plausible Analytics

Plausible offers a simpler privacy-focused service and useful basic web
analytics. Its narrower event and experimentation model would require a second
platform for the planned feedback loop.

## Mixpanel and Amplitude

Both provide mature behavioural analytics. Their product and pricing models
were heavier than this project needed, while PostHog combined the required
analytics, experiments, flags, and an open-source exit path in one platform.

# Consequences

## Positive

* One browser SDK supports events, funnels, experiments, and feature flags.
* The EU-hosted service fits the required data-residency boundary.
* The platform can be self-hosted if the managed service no longer fits.
* The first-party proxy keeps endpoint routing under the site's deployment.
* Custom events remain explicit, reviewable application code.

## Negative

* `posthog-js` adds browser JavaScript and network requests.
* Analytics data depends on an external service and its retention controls.
* The `/ingest/*` proxy is application infrastructure that needs tests and
  endpoint maintenance.
* Browser analytics is incomplete when JavaScript is disabled or blocked.
* A broad platform makes it easy to enable collection that the product policy
  has not approved.

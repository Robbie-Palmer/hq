# Vision

Make the final writing artifact as strong as the research and thinking that
produced it.

Long agent sessions excel at research, discovery, criticism, and working through
half-formed ideas. Their raw output often proves miserable to
share. It repeats itself, flattens the author's voice, over-explains simple
points, and asks readers to spend more energy than the ideas deserve. People who
read a lot of AI writing become overwhelmed and demoralized by it.

Writing should teach, motivate, and leave the reader with energy. Rewriting the
whole thing by hand should not be the only reliable way to get there.

# Product thesis

Grammarly combines different levels of intervention. It can
flag a local error, suggest a sentence, rewrite a passage, or let the writer
ignore it. An agent-first editor should do the same while accepting much larger
and messier inputs, including research sessions, plans, ADRs, and drafts built
by multiple models.

The system should build quality in layers:

1. Fast deterministic rules catch known problems and give exact feedback.
2. Lightweight models classify style problems and propose local corrections.
3. More capable models handle changes that need wider context.
4. A human accepts individual suggestions, reviews a readable diff, or approves
   a confident rewrite according to the risk and type of artifact.

This follows the same pattern as agentic code review. Cheap checks handle what
they can prove. Expensive judgment is reserved for the remaining uncertainty.

# Current state

The Personal Knowledge Graph runs Vale against changed prose. Its custom rules target the
patterns that make agent writing tiring to read. This makes agent-authored work
more bearable and catches problems before review.

I ran GECToR-2024 across a frozen cohort of five ADRs and four project pages.
After adding Markdown-aware segmentation, it returned 114 suggestions in 81
proposals. A few exposed missing articles, prepositions, and pronouns, but most
damaged Markdown, technical terms, brand names, contractions, or sentence
meaning. The useful corrections needed human
review and the result still did not close the gap between a technically correct
draft and something I wanted to publish. Generic grammatical error correction
is not enough.

The shared `writing-editor-domain` package defines records for findings,
suggestions, grouped proposals, and editorial decisions. Every record refers to
hashed source bytes through a half-open UTF-8 span. Stable IDs retain producer
and revision provenance as records pass through review and evaluation.

The DVC evaluation pipeline extracts pinned source and published revisions,
freezes train, validation, and holdout membership, and runs Vale through the
shared finding contract. It aligns findings with observed published edits while
keeping boundary-crossing cases separate for manual adjudication. Git can show
that prose changed, but it cannot turn a detection-only finding into an
accepted suggestion. Scoring therefore uses explicit editorial outcomes and a
reproducible rewrite baseline. The private DVC evidence now records accepted,
rejected, and changed decisions with exact before and after bytes and
hash-bound review receipts.

Grammarly remains the practical baseline for the final mile, but it does not
provide the API needed for an agentic publishing system. Its published research
and descriptions of its correction approach provide useful prior work without
making its private product reproducible.

# Product behavior

The editor should support three levels of control:

* Inline suggestions for local problems, each with a source span, proposed
  replacement, reason, and confidence
* A proposed rewrite shown as a diff when changes depend on one another
* Automatic rewriting for narrow, high-confidence rules, followed by final
  review when the artifact will be published under somebody's name

The user should be able to move between them. A deterministic punctuation fix
does not need the same ceremony as restructuring an argument.

## Editorial data flow

The implemented path runs repository text through Vale, GECToR, and a narrow
punctuation candidate. Vale stores detection-only findings against hashed
source bytes. The model producers emit suggestions and grouped proposals, which
enter a governed review stage. An observed edit is not an acceptance decision.
Solid blue nodes and lines are implemented. Passage rewrites remain review-only
until their evidence gate passes.

Read left to right, with two different records leaving analysis. A rule that

accept, reject, or change decision as evaluation evidence. No stage may publish
in the author's name without that review.

# Evaluation data

The useful dataset should capture more than a generic collection of
grammatically correct text. It records the decisions made while turning rough
work into published work:

* raw notes and agent output;
* early drafts and later revisions in git;
* Vale findings;
* Grammarly suggestions where they can be captured legitimately;
* accepted and rejected edits; and
* the final published artifact.

This can test whether an edit improves clarity while preserving facts, intent,
terminology, and voice. Acceptance rate supplies evidence. A system that
makes timid edits could achieve a high acceptance rate while adding little
value.

## Repository-wide GECToR pilot

The GPU pilot now separates two current-content audiences. The customer corpus
contains 89 blog posts, ideas, initiatives, project pages, and pitches. The
developer corpus contains 220 ADRs and 93 first-party guides, runbooks, and
package documents. Mirrored skills, vendored text, licences, and captured source
documents stay outside the developer corpus.

A 20-document calibration compared the original thresholds with balanced and
strict profiles for each audience. The strict profile reduced the first full
run to 106 customer-content proposals and 224 developer-content proposals. The
governed evidence contains 411 outcomes across the seed and broad cohorts: 87
accepted, 9 changed, and 315 rejected. Manual review accepted clear grammar and
preposition corrections, but also rejected changes that broke punctuation,
contractions, product names, technical meaning, or Markdown. The model
therefore remains a review-only baseline. The pinned scorecard recommends
rejecting default adoption because useful-edit yield is 23.4%, below the 25%
rejection threshold. Its generated files are never copied over the source
documents. The holdout decisions remain evaluation-only and are excluded from
future training or threshold tuning.

## Missing-comma candidate

The broad review exposed one useful narrow gap. Reviewers accepted 34 of 41
single-comma insertions from GECToR. A pre-registered experiment tested the
140M-parameter `Horizon-Labs/punctuation-restoration-small` model against those
fixed decisions. The candidate emitted 43 comma-only proposals across the 166
documents that contained reviewed GECToR proposals. It recovered 4 of the 34
accepted sites and none of the 7 rejected sites. This gives 100% useful yield
on the four matched sites but only 11.8% recall. The target RTX 4080 run took a
median 148.7 ms per artifact and peaked at 303.6 MiB of allocated CUDA memory.
Both hardware limits passed.

Another 39 proposals fall outside the fixed decisions. Their effects on facts,
terminology, intent, and voice have not been reviewed. The experiment therefore
ends with `gather-more-evidence`. The model stays out of the default editor.

# First useful release

The first release should work on content in this repository before becoming a
general editor:

1. Define a versioned suggestion format with source spans, replacements,
   categories, reasons, confidence, and model or rule provenance.
2. Build an evaluation set from ADR and project-page revisions, including the
   GECToR-2024 result as a baseline.
3. Measure factual preservation, unwanted voice changes, accepted edits, time
   saved, and regressions caught by deterministic rules.
4. Run Vale and other deterministic checks through the shared finding format.
5. Evaluate lightweight models only for failure classes that the evaluation
   set proves Vale cannot handle. The first missing-comma candidate needs more
   evidence and is not part of the default editor.
6. Add passage rewrites with diffs after local suggestions are reliable.
7. Capture accept and reject decisions so the evaluation set grows through use.
8. Extract the repository-specific implementation into a general product only
   after it improves real published pages.

The repository reviewer now accepts one byte-bounded passage rewrite and
decomposes it into ordered ADR 003 suggestions under a grouped proposal. Before
the decision prompt it shows the combined diff, project and ADR citations,
terminology context, evidence freshness warnings, and the author's retained
fact-checking and publication authority. Per-case evaluation records facts,
terminology, voice, useful-edit yield, and review time. The default-loop gate
stays closed until every declared threshold passes.

# Relationship to the knowledge graph

The knowledge graph supplies the context that generic writing tools lack. It
can tell the editor which project a draft describes, which ADR contains the
source decision, what terminology the author uses, and which claims need fresh
evidence. The editor returns proposed public artifacts and structured edit
history. It does not decide what is true or publish in the author's name without
the authority to do so.

# Success

The editor succeeds when people prefer reading its output to the raw agent
draft, authors keep their voice, and publishing takes less manual rewriting.
It fails if it merely produces more polished AI prose with the same cognitive
load underneath.

# Non-goals

* Replacing research, fact checking, or editorial judgment
* Training one universal style into every author
* Treating grammatical correctness as the whole measure of quality
* Automatically publishing essays under a person's name
* Adding a large model to problems a deterministic rule can solve
